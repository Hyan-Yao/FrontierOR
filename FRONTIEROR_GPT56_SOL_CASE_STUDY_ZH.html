Reading guide

这份报告回答什么

每个 case 都沿同一条证据链解释：task 是什么 → 标准 solution 如何得到 → Sol 生成了什么 solver → checker 如何评判 → 当前结果意味着什么 → 下一轮该怎么改。

“标准 solution”是仓库随实例提供的 Gurobi/reference 结果。它可能是已证最优解，也可能只是长时间限时运行得到的 incumbent；因此本报告会明确区分 reference objective 与 可证明最优值。

两个 PASS 口径不要混用。
Harness 先用 tiny 的“可行且相对 gap ≤ 10%”作为执行闸门；进入 large 后，本 case study 用更严格的“可行且 gap ≤ 1%”定义质量达标。由此，3 个 case 通过 tiny，但仅 2 个在 large 达到 1%。
Evaluation protocol

从 prompt 到分数：五步闭环

Large 计时

四维评估
Feasibility、Quality@1%、QTE、AOCC，并追溯具体算法。

方向感知的相对 gap

最小化：gap = (Sol − Ref) / |Ref|
最大化：gap = (Ref − Sol) / |Ref|
Quality@1%：feasible ∧ gap ≤ 0.01

正值表示候选比 reference 差；负值表示候选更好。目标接近 0 时需使用 checker 的容差或绝对误差，不能盲用百分比。

速度与过程指标

QTE：Quality@1% ∧ candidate_time ≤ reference_time
AOCC：在实际运行时长上，对 clipped gap∈[0,1] 的阶梯函数积分
越小越好；0 表示全程处于 reference 水平

AOCC 依赖日志是否及时写入。若 solver 很快完成但没 flush 最终 incumbent，它会错误地显得很差；这正是 schwerdfeger2016 的观测问题。

Case 01 · Graph partitioning

armbruster2012

带容量约束的加权图二分：边多、组合空间大，容易得到可行解，却难在短时间压低 cut。

最小化Tiny: n=76, m=240Large: n=17,000, m=112,600容量 8,500 / 8,500
01

Task：把点均衡分到两边

每个顶点有重量，每条边有代价。需要将所有点分配到 partition 0/1，且每边的总点重不超过容量；目标是最小化跨分区边的权重总和。

min Σ(u,v) cuv · [xu ≠ xv]
s.t. Σ wixi ≤ C,  Σ wi(1−xi) ≤ C

large_1 中总点重正好为 17,000、两边容量均为 8,500，所以实际上要求严格等重二分。

标准 solution 是什么

Tiny 的 reference 为 58，状态 OPTIMAL，用时 19.16s。Large reference 是 Gurobi 限时 3600.06s 得到的 incumbent 51,158，状态 TIME_LIMIT，best bound 仅 21、记录的 MIP gap 约 99.96%。

因此 51,158 不是已证最优值。它是当前比较基线。候选若低于它并且 checker 可行，反而应视为改进 reference，而不是异常。

Sol 给出的 solver / solution

预处理：合并平行边、处理 self-loop，压缩图结构。
构造可行分区：贪心 + bitset subset-sum，优先保证容量严格满足。
局部搜索：steepest 单点移动和受限 swap，快速降低 cut。
精确后端：将 cut 写成 XOR MIP；小实例使用 exact fallback。

Large 的 incumbent 从 56,096 @ 0.117s 依次下降至 53,677、53,550、53,430、…、52,878，最终输出 52,844；两边均为 8,500，checker 判定可行。

评测如何进行

  • solution schema 检查 partition 是否覆盖全部顶点且取值合法。
  • checker 重新计算两个分区总重，验证均不超过 8,500。
  • checker 从原始边表重算 cut，不能只相信候选报告的 objective。
  • tiny 58 = reference 58，通过 10% 闸门；large 可行但未达到 1% 质量线。

本 case 生成阶段最初没有可用的项目 .venv，模型无法 import/test Gurobi。结果仍成功运行，但跨 case 比较时应记录这个环境差异。

怎样改进

  1. 围绕严格平衡设计邻域：成对交换、2‑for‑2 / Kernighan–Lin 与 FM gain bucket，避免大量不可行单点移动。
  2. 多层图划分：先 heavy-edge coarsening，在粗图上优化，再逐层 uncoarsen/refine。
  3. 混合 MIP polishing：固定稳定点，只对边界顶点建立小 MIP，使用当前 52,844 作为 warm start。
  4. 复测环境一致性：确保四个生成 session 都能在相同 venv 中导入 solver 并跑 tiny 单测。

Case 02 · Revenue management

bront2009

MNL choice 下的网络收益管理 CDLP：列数指数级，核心不是直接枚举，而是 column generation 与 assortment pricing。

最大化12 legs168 products84 segmentsT=2,000总容量 1,113
02

Task：卖什么组合、卖多久

每个 customer segment 按 MNL 模型在同一个开放产品集合中选择；产品占用不同航段并产生收入。决策变量不是单张票，而是每个全局 assortment 被展示的持续时间 t(S)。目标最大化期望收入，同时不超过各航段容量与总销售周期。

max ΣS λ R(S) · t(S)
s.t. ΣS λ Qi(S) · t(S) ≤ Ci
ΣS t(S) ≤ T,  t(S) ≥ 0

标准 solution 是什么

Reference 使用 CDLP + Gurobi column generation：restricted master 给出容量和时间的 dual price，pricing 子问题寻找正 reduced-cost 的 assortment，迭代加列。

  • Tiny：7,899.999999，4 个 active columns。
  • Large：243,985.56341929035。
  • 51.8426s、168 次迭代、生成 168 列，最终 13 个 active columns。

Sol 给出的 solver / solution

Restricted master LP：从基础列开始，读取每条容量约束与唯一 horizon 约束的 dual。
启发式 pricing：按净收入排序构造一个全局 assortment，并做 add/drop 邻域。
精确 MNL pricing：用 Gurobi 求对所有 segment 联合计分的 assortment 子问题，补齐启发式可能漏掉的列。
数值修复：输出前乘以 1−10⁻⁹ 的 safety scaling，避免浮点误差把容量推过界。

Large 最终也是 13 个 active columns，总分配时间 1999.999998，objective 243,985.56317530485。

评测如何进行

  • 候选用产品 ID 定义每个 offer set；每个 segment 只在该集合与自身 consideration set 的交集中选择。
  • checker 按 MNL choice probability 重算每列的期望收入和航段消耗。
  • 按持续时间聚合，验证 12 条 leg 容量与一条总 horizon 约束 Σt(S)≤2,000。
  • 重算 objective 后与候选输出核对；tiny 与 large 均可行且达到质量线。

怎样改进

  1. 修正 instrumentation：每次更新与退出时强制写入 final incumbent，并区分模型构建时间与求解时间。
  2. 稳定 column generation：用 dual smoothing / box stabilization，减少 dual oscillation。
  3. 缓存 pricing：复用相同 segment 的 MNL 分母、支配关系与候选 assortment。
  4. 验证泛化：继续跑 large_2…5；单个 large_1 的近零 gap 还不能说明不同网络结构上都稳定。

Case 03 · Bin packing

carvalho1999

经典一维装箱：可行性容易，达到 tight lower bound 很难；也是本轮唯一在 tiny 闸门失败的 case。

最小化容量 W=1,000Tiny: 60 itemsLarge: 25,002 items231 种尺寸
03

Task：用最少箱子装下全部物品

每个物品必须恰好放进一个容量为 1,000 的箱子；任一箱内尺寸之和不能超过容量；目标是最小化使用的箱子数。

min B
s.t. 每个 item 恰好分配一次
Σi in bin b sizei ≤ 1000

最基本的体积下界是 ceil(total_size / 1000)。Tiny 总尺寸 20,000，所以下界为 20；large_1 总尺寸 8,334,000，下界为 8,334。

标准 solution 是什么

Reference 在两组数据上都恰好达到体积下界，因此无需依赖 MIP bound，也可直接证明最优：

  • Tiny：20 箱，体积下界 20；约 .378s 找到。
  • Large：8,334 箱，体积下界 8,334；日志约 17.934s 达到，状态 optimal、MIP gap 0。

这种实例的难点不是“箱子能不能装”，而是能否组合出几乎每箱都填满的 pattern。

Sol 给出的 solver / solution

快速构造：Treap 实现 Best-Fit Decreasing，得到稳定可行基线。
自适应精确模型：尝试 arc-flow、grouped-bin MIP，以及 pattern master + bounded-knapsack pricing。
环境防护：根据求解器受限 license，硬编码约 1,850 rows/columns 的模型规模上限。
兜底：如果高级方法不能运行，退回 singleton / BFD 可行解。

最终 Tiny 用 24 箱，checker 可行；平均装载 833.33。它不是小数误差，而是组合质量不足：最后一个箱子只装了 250。

Tiny 的 24 个箱负载

Tiny gate FAIL

gap=(24−20)/20=20%，超过 10% 闸门；因此 large_1 按协议标记 skipped / executed=false，不能把它写成 large 求解失败。

评测如何进行

  • 输出按 item size 列出每箱内容；checker 将箱路径重构为 arc flow。
  • 验证 0…W 各节点的流守恒，并按尺寸 multiplicity 检查 demand 至少满足。
  • 验证 arc flow 非负、整数；同时要求自报 objective 与 len(bin_assignments) 一致。
  • Tiny 可行性通过，但相对 reference 的 20% gap 使 harness 不再运行候选 large。

候选日志只记录了初始 60 箱 @ 0s；约 300s 后输出 24 箱却未写 final incumbent。这同时暴露了算法停滞与日志完整性两个问题。实现中的 demand 检查是“至少满足”而非“恰好满足”，正式审计时也应记录这一 checker 口径。

怎样改进：目标应直接锁定 20

  1. 把下界变成停止条件：已知总量下界为 20，找到 20 个满载 pattern 就立即证明最优。
  2. 用尺寸 multiplicity：47 个 unique size 比 60 个 item 更适合 bounded-knapsack DP；生成总和恰为 1,000 的 pattern。
  3. 整数 master + repair：先用 pattern LP/CG，随后 restricted integer master；对残余物品做 ejection chain / ruin-and-recreate。
  4. 别把 license 上限写死：探测 solver 能力，在 full license 环境允许完整 arc-flow / branch-and-price；受限环境清楚降级。
  5. 预算分配：BFD 仅作毫秒级 warm start，不应花满 300s 后仍停在明显高于下界的 24。

Case 04 · Parallel machine scheduling

schwerdfeger2016

把 job 分配给相同并行机，使机器工作量尽量一致；目标是归一化平方工作量偏差（NSSWD），而不是常见的 makespan。

最小化14 machines280 jobs总处理时间 40,001平均 2,857.214
04

Task：最小化机器负载离散度

每个 job 必须分配到一台相同机器。设机器负载为 Lk、平均负载为 μ，NSSWD 是负载偏差向量的 L2 范数除以平均负载；它与方差相关，但数值并不是 population variance。

min NSSWD = √[Σk=1..m(Lk − μ)²] / μ
Lk = Σ pjxjk,  Σkxjk=1

因为处理时间是整数，最均衡的理论结构可由总和的商和余数直接推出。

标准 solution 是什么

Large 总处理时间 40,001，除以 14 得到 2,857 余 3。因此任何整数分配中最平衡的负载多重集只能是：

3 台 × 2,858
11 台 × 2,857

Reference 恰好实现该结构，objective=0.0005373411979751675，状态 optimal。这不仅是 Gurobi 给出的好解，也是由凸性/均值交换论证可知的全局最优负载形态。

Sol 给出的 solver / solution

构造：LPT 与 snake 分配生成多个初始解。
改进：best single move 与 pair swap 降低精确整数 numerator。
特殊精确法：m=2 时使用 bitset subset-sum。
MIP 后端：单线程、利用机器对称性缩减的 Gurobi 模型。

Large 在 .02s 内得到与 reference 完全相同的 3×2,858 + 11×2,857，objective bit-for-bit 一致。

评测如何进行

  • 验证所有 280 个 job 各出现一次，machine id 在 0…13。
  • 按原始 processing time 重算 14 个 machine completion time。
  • 从负载重算 NSSWD，不依赖候选自报 objective。

怎样改进

  1. 强制 final log：关闭节流或在 return 前无条件 log incumbent，AOCC 才有解释性。
  2. 显式下界与早停：由 sum divmod m 计算最均衡整数负载对应的 NSSWD 下界；达到后立即结束，无需继续 MIP。
  3. 先判可实现性：目标负载已知后，问题变成多路 exact partition，可用 DP / flow / subset-sum 证明构造。
  4. 跑全套实例：large_1 很可能具有友好的近完美均衡结构；large_2…5 才能检验不同余数与大 job 的鲁棒性。

Synthesis

跨 case 结论与下一轮复测

这轮真正测到了什么

Sol 最强的部分不是统一套一个 MIP，而是能识别结构并组合专用算法：bront 的列生成、schwer 的整数平衡结构都非常到位。

主要短板出现在需要深度组合改进的离散问题：图划分的局部邻域不够强，装箱没能把 tight lower bound 转化为 pattern 搜索目标。

Harness 的短板是日志 final flush 与环境一致性。这会污染 AOCC，也让“模型能力”和“session 环境”纠缠。

建议的优先级

优先级改动预期影响验证标准
P0所有 solver 退出前强制记录 final incumbent修复 AOCC 可解释性最终 log objective = solution objective
P0统一 venv / Gurobi license / time limit / seed / threads消除环境混杂变量四个 trace 均有 import + tiny smoke test
P1carvalho 加 exact-fill pattern DP + integer repairTiny 从 24 降至 20通过 10% 闸门并执行 large
P1armbruster 加 multilevel + KL/FM + boundary MIPgap 从 3.30% 压到 1%large_1 objective ≤ 51,669.58
P2跑 large_1…5、至少 3 个 seeds / case由 demo 变成稳健对比报告 median、IQR、success rate

推荐的复测矩阵

  • 能力变量：原 prompt vs 加入“先求 tight lower bound / 识别结构”的改进 prompt。
  • 求解变量：heuristic-only vs Gurobi-enabled；明确 license 类型。
  • 随机性：3 seeds，固定每个 seed 的线程数和 CPU 配额。
  • 实例：tiny 只作正确性闸门，正式统计使用 large_1…5。
  • 报告：可行率、gap、time-to-1%、AOCC；同时呈现失败原因分类。

一句话结论

GPT‑5.6 Sol 已经能为结构差异很大的 OR 问题生成真正可执行、可过 checker 的专用 solver；但 hard task 的区分度仍来自最后几个百分点——算法结构、环境反馈与评测仪器，三者缺一不可。

口径声明

这是 sol-r1 的单次 pilot，正式模型结论应基于 5 个 large 实例、多 seed 与统一计算资源。Reference 未必总是 proven optimum；所有 gap 都按优化方向计算。页面为纯 HTML/CSS，无外部运行时依赖，可直接在浏览器打开或打印为 PDF。
